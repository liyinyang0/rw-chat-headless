# rw-chat-headless — headless-клиент лобби Rusted Warfare только для чата

[中文](README.md) | [English](README.en.md) | [Русский](README.ru.md)

Заходит как игрок в комнаты Rusted Warfare, совместимые с **TCP / протоколом 176** (публичный список / код комнаты / прямой IP), обменивается сообщениями в лобби и поддерживает соединение для чата после старта игры.
**Только чат**: не становится хостом и не участвует в матче — headless-инстанс, который просто «сидит в комнате» и пишет/читает сообщения.
Чистая реализация протокола на TypeScript / Node 22+: без игрового движка, без UI, без графических зависимостей.

Этот репозиторий содержит только самого клиента. Чтобы подключить ИИ / автоответы / мост к внешним сервисам, см.
[Программный доступ](#программный-доступ-свой-бот) ниже —
логику бота вы пишете сами; клиент даёт вам событие `chat` и метод `sendChat()`.

## Возможности

- ✅ Вход по публичному списку серверов (`list` → `list:N`)
- ✅ Вход по коду комнаты: ответ на PoW, переходы 178 и последующее рукопожатие игровой комнаты; число переходов зависит от маршрута, некоторые рукопожатия используют одно TCP-соединение
- ✅ Прямое подключение по IP / домену
- ✅ Пропуск серверных блоков customUnits для чата без установки модов; серверы с дополнительной авторизацией или изменённым протоколом требуют отдельной проверки
- ✅ Ответы на запросы пароля (`PASSWORD` / API ввода) и PoW ретранслятора; область проверки описана ниже
- ✅ Приём/отправка чата (141 приём / 140 отправка), список игроков (115)
- ✅ Удаление слотов из списка, наблюдатели/ИИ, ping и совместное управление; пауза, карта при старте и уведомления об окончании игры
- ✅ Срок ожидания входа и обнаружение потери связи; опциональные повторные подключения с задержкой в CLI и мультикомнатном режиме
- ✅ Несколько комнат в одном процессе (по соединению на комнату, независимые сессии и история чата)
- ✅ Контрольная сумма базовых юнитов v176 встроена (678359601, снята с реального клиента)
- ✅ На старте игры (120) отвечает 112 с состоянием загрузки и по умолчанию сохраняет соединение; игровой симуляции нет, поэтому успешный старт и длительное присутствие в игре на всех серверах не гарантируются
- ❌ Нет хостинга и игрового управления; надёжный UDP и полная поддержка других версий протокола (включая официальный Auto Server v151) не реализованы

> Побайтовая спецификация протокола: [docs/PROTOCOL-SPEC.md](docs/PROTOCOL-SPEC.md).
> В формуле g() поле `7:` всегда использует ванильное умножение; h() — формат `#%06X`.
> Коды комнат, дескрипторы списка, адреса и бинарные перенаправления используют общий процесс подключения TCP / 176. Проверки чата двумя клиентами в публичной комнате и `rkc595` пройдены 2026-10-09; UDP, другие версии и расширения сообщества проверены не полностью. См. [изменения и результаты](docs/VANILLA-ROOM-JOIN.md).
> Исправления списка игроков, состояния и связи: [описание и результаты](docs/ROSTER-STATE-FIX.md). Парольные сценарии, разбор наблюдателей/ИИ, пауза и старт покрыты искусственными пакетами и локальными TCP-тестами. В этом цикле реальная комната с паролем не проверялась; изменения роли наблюдателя, старт, пауза и длительная работа ещё требуют проверки в контролируемой комнате. Список серверов может отставать от фактического состояния: вход иногда отклоняется даже при отображении лобби.

## Быстрый старт

Нужен Node.js 22 или новее. Linux / macOS:

```bash
npm install
cp .env.example .env        # при необходимости поменяйте NAME и др.

node --env-file=.env --import tsx src/cli.ts list
node --env-file=.env --import tsx src/cli.ts join list:0
```

Windows PowerShell:

```powershell
npm install
Copy-Item .env.example .env  # отредактируйте .env
node --env-file=.env --import tsx src/cli.ts list
node --env-file=.env --import tsx src/cli.ts join list:0
```

CLI читает переменные окружения процесса; `--env-file=.env` явно загружает файл. Уже заданные переменные имеют приоритет над одноимёнными значениями файла. Без файла можно использовать `npx tsx src/cli.ts ...`, который не загружает `.env` автоматически. В одной комнате вводите текст для чата, `/quit` для выхода; закрытие stdin также завершает работу.

Формы цели: `list:N` / код комнаты (напр. `rkzxxxx`) / `1.2.3.4:5123` / полный дескриптор `get|id|code|pwd|port`. Индексы публичного списка начинаются с 0 и могут меняться при обновлении. В оболочке заключайте полный дескриптор в кавычки, чтобы `|` не стал конвейером.

## Несколько комнат в одном процессе

Один процесс одновременно в нескольких комнатах (по протоколу одно соединение живёт ровно в одном лобби; больше комнат = больше соединений):

```bash
node --env-file=.env --import tsx src/cli.ts join-multi list:0 list:2 list:5
```

- Базовый UUID каждой сессии получает суффикс `-m1/-m2/…`, затем идентичность выводится с учётом serverUuid каждого хопа
- Имена со 2-й сессии получают суффикс (name, name-2, …), уменьшая конфликты; `MULTI_NAME=same` отключает это. Сервер всё равно может переименовать игрока или отклонить одинаковые имена
- Сессии стартуют со сдвигом (`MULTI_STAGGER_MS`, по умолчанию 1200); падение одной комнаты не влияет на остальные
- Команды stdin: `/rooms` (таблица статусов), `/say <номер> <текст>`, `/sayall <текст>`, `/quit`; номера комнат здесь начинаются с 1, в отличие от `list:N` публичного списка
- Историческая метка `roomId` в `/rooms` фактически показывает serverUuid, а не введённый код комнаты, и не обязательно уникальна; сверяйте также цель подключения и список игроков
- `MULTI_LIFETIME_MS=60000`: автоматический выход по истечении времени (для автономных тестов)
- Последние 200 сообщений чата каждой комнаты хранятся в памяти (`handle.history()`)
- Закрытие stdin в мультикомнатном режиме не завершает работу; выход через `/quit`, SIGINT/SIGTERM или срок жизни. Цели также можно разделять запятыми
- Исторические оценки памяти: около 40 МБ на один экземпляр, 70 МБ базово для мультикомнатного процесса, +1 МБ на дополнительную комнату. Полные условия измерений не сохранены, поэтому это только ориентир. Расход зависит от Node, платформы и трафика; игровые кадры всё ещё принимаются и собираются, большие карты/сохранения могут временно увеличить память. Измеряйте RSS/heap по журналу запуска и во время работы

## Программный доступ (свой бот)

Помимо CLI, `Session` — готовая к использованию библиотека. Входящий чат — событие `chat`, отправка — `sendChat()`:
LLM, движки правил, мосты сообщений — всё подключается здесь:

```ts
import { Session } from "./src/client/session.ts";
import { parseConnectTarget, resolveTarget } from "./src/masterserver/target.ts";

const target = await resolveTarget(parseConnectTarget("1.2.3.4:5123"), null);
const session = new Session(target, { playerName: "my-bot" });

session.on("chat", (chat) => {
  if (!chat.senderName) return; // пропуск системных сообщений
  // Без информации о слотах не отвечать автоматически на нераспознанное своё эхо.
  if (chat.senderTeamId === null || chat.senderTeamId < 0 || session.yourTeamId < 0) return;
  if (chat.senderTeamId === session.yourTeamId) return;
  // ↓ здесь ваша логика: вызов LLM, срабатывание правил, пересылка на другую платформу…
  session.sendChat(`echo: ${chat.message}`);
});

session.on("stateChange", (s) => console.log("state:", s));
await session.start();
```

`senderTeamId` и `yourTeamId` обозначают слоты игроков текущего соединения, а не имена или номера союзов. Клиент с функциями союзов может добавлять префиксы при отображении имени; сервер тоже может переименовать игрока при совпадении имён. Не определяйте себя по фиксированному имени или удалению цифрового префикса. Старые форматы чата не передают слот отправителя; пример пропускает автоответы, пока надёжное сопоставление идентичности не проверено отдельно.

`session.roster` — текущий список игроков (ИИ / наблюдатели / ping / совместное управление). `connectionActive` означает недавнюю активность по серверному ping, а не текущее состояние TCP. `session.info.serverUuid` — идентификатор сервера; общий ретранслятор может использовать его в нескольких комнатах, поэтому одного этого поля недостаточно для определения комнаты.
Оркестрация нескольких комнат — через `runMultiRooms()` (см. `src/client/multi.ts`), по одному handle на комнату.

Для серверного ввода слушайте `inputRequest` и вызывайте `request.respond(answer)`; `null` отменяет соединение. Можно вернуть ответ из `SessionOptions.onInputRequest`. В CLI одной комнаты следующая строка становится ответом; неизвестный запрос 117 ждёт ввод до 60 секунд по умолчанию. Для комнаты с паролем из публичного списка `PASSWORD` нужен до разрешения адреса. Мультикомнатный API принимает `onInputRequest`; в мультикомнатном CLI нет команды для ответа на произвольный запрос отдельной комнаты.

Слушатели состояния той же `session` регистрируйте до `start()`:

```ts
session.on("settingsChange", settings => console.log("paused:", settings.gamePaused));
session.on("phaseChange", phase => console.log("phase:", phase));
session.on("gameStart", start => console.log("map:", start.mapType, start.mapPath));
session.on("gameEnded", () => console.log("round ended"));
```

Состояние соединения `state` и фаза игры `phase` независимы; пауза не означает возврат в лобби. `gameEnded` сообщает о серверном завершении раунда или возврате после игры в лобби один раз за раунд, а не об отключении TCP. Во время игры карту берите из `gameStartInfo?.mapPath`, в лобби — из `roomInfo?.mapPath`; до получения нужных пакетов значения могут отсутствовать.

Для опционального переподключения замените создание сессии выше на:

```ts
import { ReconnectingSession } from "./src/client/reconnecting.ts";

const session = new ReconnectingSession("rkzxxxx", { playerName: "my-bot" }, {
  enabled: true, maxRetries: 10,
});
// Подключите слушатели выше, затем await session.start().
// session.disconnect() завершает работу и отменяет дальнейшие повторы.
```

Обычная `Session` обнаруживает разрыв, но не повторяет подключение; используйте её, если повторами управляет внешний Worker. Повторный вход восстанавливает чат, а не игровую симуляцию, и не гарантирует прежний слот.

## Контрольная сумма юнитов (UNITS_CHECKSUM)

Константа v176 678359601 встроена по умолчанию. Другую контрольную сумму можно снять инструментом захвата; иной версии также могут понадобиться изменения структуры пакетов, поэтому одной замены константы недостаточно для совместимости:

```bash
npx tsx tools/capture-server.ts 5123     # слушает 127.0.0.1:5123 (автоответ 161 для синтеза)
# реальный клиент → Multiplayer → Direct Join → 127.0.0.1:5123
# консоль печатает ★ контрольную сумму / сравнение формулы g() / формат h()
# Задайте снятый UNITS_CHECKSUM в .env и войдите командой с --env-file выше.
```

## Переменные окружения

См. [.env.example](.env.example): `NAME` / `PASSWORD` / `LANGUAGE` / `REGISTER_FORMAT` /
`UNITS_CHECKSUM` / `RELAY_ROOM_ID` / `CLIENT_UUID` / `RW_SOCKS_PROXY` / `DEBUG`.

По умолчанию Session даёт на вход 45 секунд вместе с переходами ретранслятора; после входа отсутствие полного кадра протокола в течение 60 секунд приводит к отключению. Настройки: `JOIN_TIMEOUT_MS` и `RECEIVE_TIMEOUT_MS`, 0 отключает соответствующий таймер Session. Ожидание серверного ввода приостанавливает бюджет входа и использует отдельный тайм-аут. Тишина в чате или отсутствие ответов 109 на клиентские пакеты 108 сами по себе не означают потерю связи.

Мультикомнатный runner также имеет отдельное ожидание завершения запуска, по умолчанию 45 секунд; при превышении ещё не вошедшие сессии закрываются. Значение `JOIN_TIMEOUT_MS=0` или большее значение само по себе не отключает и не продлевает это ожидание. В библиотеке его задаёт `settleTimeoutMs`.

Для CLI / мультикомнатного режима включите `AUTO_RECONNECT=1` (по умолчанию выключено). Каждый повтор заново разрешает исходную цель, сохраняя базовый UUID и SOCKS-прокси. Значения по умолчанию: `RECONNECT_MAX_RETRIES=10`, `RECONNECT_BASE_MS=5000`, `RECONNECT_MAX_MS=60000`; ожидание 5/10/20/40/60 секунд с небольшим случайным отклонением, максимум 60 секунд. Успешный вход не сбрасывает общий бюджет повторов. При кике, отсутствии комнаты или ручном выходе повторы прекращаются. В библиотеке явно используйте `ReconnectingSession`, не дублируя цикл внешнего Worker. См. [описание жизненного цикла](docs/ROSTER-STATE-FIX.md).

## Идентичность клиента (одна на развертывание, по умолчанию постоянная)

Идентичность клиента перед сервером (clientId) выводится из UUID клиента: `SHA256(uuid + serverUuid каждого хопа)` (64 шестнадцатеричных символа в верхнем регистре),
имитируя поэтапное выведение в реальном клиенте. Поведение этого UUID по умолчанию:

- **Генерируется случайно при первом запуске**, сохраняется в `data/client-uuid` — своя на каждое развертывание,
  стабильна между перезапусками процесса (от неё зависят переподключение с той же идентичностью и распознавание сервером)
- Сменить идентичность: удалите `data/client-uuid`, затем перезапустите процесс, или задайте `CLIENT_UUID` явно
- Контейнеры / CI без постоянного диска: задавайте `CLIENT_UUID` явно, иначе каждая пересборка контейнера — новая идентичность
- `data/` уже в `.gitignore`, файл идентичности случайно не попадёт в коммит

Для сохранения идентичности каталог `data/` должен быть доступен для записи; в режиме только чтения идентичность действует лишь в текущем процессе. Разным развёртываниям нужны отдельные каталоги данных или явно заданные UUID.

В режиме нескольких комнат все сессии используют один базовый UUID, различаясь только суффиксами слотов `-m1/-m2/…`.
После изменения хеша с нижнего регистра на верхний, как в оригинале, сервер может распознать новую идентичность даже при прежнем базовом UUID.

## Инструменты (tools/)

- `capture-server.ts` — фейковый сервер, снимающий отпечаток регистрации / контрольную сумму реального клиента
- `proxy-capture.ts` — MITM-прокси для захвата пакетов
- `probe.ts` — быстрая проверка поведения целевого сервера
- `GoldenG.java` / `golden-g.txt` — эталонная реализация формулы g() и тестовые векторы
- `dump-descriptors.mjs` — печать дескрипторов пакетов

## Этикет использования

Этот клиент заходит на **чужие серверы**. Соблюдайте:

- Серверы могут ограничивать частоту соединений и сообщений своими порогами; сохраняйте задержки повторного подключения и ограничивайте частоту ответов бота
- Честно обозначайте бота (заметное имя), не выдавайте себя за человека
- Не зависайте в чужой комнате без согласия хоста; выгнали — уходите
- Введённый код комнаты обычно автоматически отвечает на явный запрос её номера через 117; `RELAY_ROOM_ID` служит переопределением при прямом входе на ретранслятор (`new` создаёт комнату с ролью хоста, что не поддерживается)
