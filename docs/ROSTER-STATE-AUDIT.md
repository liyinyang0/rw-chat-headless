# 名册、房间状态与失联检测研究

日期：2026-10-09。研究对象：独立仓库 `main` 首次提交 `9fd92ad`、当前 `codex/vanilla-room-join` 的 `fedea7a`，以及 CNKD 项目本地 `headless-client`。本轮只研究与复现，没有修改运行代码、合并 main、改变密码流程或重启生产服务。

## 结论

统一入房和真实聊天的上一轮验收仍有效，但不能据此认为名册字段也准确。名册有多处原有语义错误，建议在合并前追加修复。连接检测应补在会话层，业务层已有的退避重连可以继续复用。

依据是 `rw_analysis/02-decompiled` 与 `02b-decompiled` 的原始读写逻辑及调用链，不依赖 03 中的可读字段命名。构造包和 localhost TCP 观察结果保存在 [ROSTER-STATE-REPRO.json](ROSTER-STATE-REPRO.json)。没有重新加入真实房间。

## 1. 名册不是“部分槽位的增量集合”

115 对全部 `count` 个槽位逐个写 `exists`。记录不存在时，原版读侧删除对应槽位，精简记录模式也一样删除。

证据：`02b/.../gameFramework/j/ad.java:2385-2443`、`:3310-3374`，交叉对照 `02/.../j/ad.java:1883-1936`。

当前 `parseTeamList` 遇到 `exists=false` 直接跳过；`mergeRosterDelta` 从旧名册开始，仅覆盖存在的记录，因而丢失删除信息。

更重要的是，精简记录的线格式是：

```text
byte 0                 保留/格式字段，不是槽位编号
int team.A()           服务端报告的 ping 或特殊状态值
boolean team.I         手动共享控制
boolean team.J         自动共享控制
```

槽位来自 115 的循环下标。证据：`02b/.../game/n.java:163-176`，`02/.../game/n.java:173-188` 的对应写读函数。当前把第一个字节当 slotId，把两个共享控制值当网络在线状态。

本地复现：旧名单有槽位 0、1、2，精简包只保留槽位 1，且其 ping=55。当前解析出槽位 0，ping=-1；合并后仍有 0、1、2。真实后果可能是开局后的在线状态更新写错玩家、已离开的玩家残留、房主离开无法正确判断。

修正方式：明确精简记录只是字段精简，槽位存在性仍是完整快照。可以返回 `removedSlots` 并同时处理 count 缩小，或按本包存在的槽位构建新名单，再从旧名单继承该槽位未传的名字、联盟、颜色等字段。

## 2. 完整名册的几个字段语义错位

完整记录的原始发送函数为 `02b/.../game/n.java:116-159`，读侧 `:183-267`；两份反编译的线路结构一致。

| 原始字段/位置 | 原版语义与依据 | 当前解释 | 应修正 |
|---|---|---|---|
| 联盟编号 `r` | `n.b()` 返回 `r == -3`，`:398-400` | 联盟字段保留，但未用于观战 | `isSpectator = allyTeamId === -3` |
| 第一个 ping int `A()` | `:895-910` 使用 ping 时间计算数值；109 在 `ad.java:2097-2115` 更新 W/X | 被跳过为 teamNetworkId | 保留服务端报告的 ping，完整与精简格式一致 |
| 版本 >=55 的 bool `w` | 构造时 `w = this instanceof AI`，`:1115` | isSpectator | AI 标志；不能用来判断观战 |
| 紧跟 w 的 int `x` | `n.C()` 的 AI 难度逻辑，`:928-946` | pingMs | AI 难度 |
| 两个 bool `I/J` | `ad.java:5617-5637` 开关手动共享控制；`:3215-3271` 设置掉线/AFK 自动共享控制 | connectionActive/netActive | 分别保留手动与自动共享控制 |
| int `Q` | `n.c(bool)` 设置为 0/1，`:664-674`；服务器 `ad.O()` 对 `this.z == team` 调用它，`:3206-3210`；UI 在 `n.z()` 展示 HOST | hostFlag，语义未验证 | 原版静态证据支持 Q==1 为房主标志；社区节点仍需真实包核对 |

原版 `n.A()` 返回的特殊值包括 -99（主机显示 HOST）、-1（ping 过期）、-2（无 ping 记录）；这是服务端报告的状态，不能简单等同于该玩家 TCP 连接的严格实时状态。客户端可保留原始 ping，派生“最近在线/过期/未知”，不要再从共享控制 bool 推断在线。

本地完整包的复现结果：

- 观战人类：联盟=-3、ping=42、AI=false；当前返回非观战、ping=2。
- AI：联盟=1、ping=-2、AI=true、难度=3；当前返回观战、ping=3。
- host：ping=-99、两个共享控制 bool=false；当前返回 connectionActive=false。

这里也解释了上轮实测日志中“名册有真人但 active players=0”的现象：字段误解影响人数统计，并不表示入房或聊天失败。

## 3. 房间状态：已有内容与缺口

106 已解析地图、经济、禁核、队伍锁、房间锁、观战允许等设置，不需要重复实现。120/122 已有 `phaseChange`，表示开局和回大厅。

115 设置段版本 >=4 的尾部是 `sharedControl`，>=5 再跟 `gamePaused`。两份原始读写函数一致：`02b/ad.java:2488-2493`、`:3348-3349`，`02/ad.java:1974-1978`、`:3047-3048`。`02b/ad.java:5870-5875` 的暂停/继续方法确认 `al` 含义。

当前解析在 customUnits 之后结束，两项未读。构造包将两项设为 true，当前返回对象中均不存在。

建议：

1. 在 `RoomSettingsLite` 增加这两项，并在 115 更新时通知上层。较老设置版本未提供时保持未知或沿用上次值，不要强行变 false。
2. 暂停是 `in_game` 的附加状态，不应把暂停当回大厅。连接状态、对局阶段和暂停分别表达。
3. 120 可以继续补充本轮启动的地图类型/地图路径；当前只看包类型，因此 roomInfo 可能仍是上次 106 的地图。原版包结构见 `02b/ad.java:2529-2544`、`:4470-4511`。
4. 116 是 `int + bool`，原版将 true 锁存在 `be` 并用于“Game ended by server”提示，见 `:2500-2508`、`:1569-1573`。应与 122 回大厅区别处理；现有 `gameEnded` 在 122 触发，不能直接把 116 当相同事件而导致重复结束或误退出。

精简 115 的发送条件在原版是已经开局且先前发送过一次名单，见 `02b/ad.java:3310-3315`。它可作为辅助阶段证据，但不能反过来认为完整 115 必定表示大厅。加入已经开局的房间需要单独验收初始阶段和地图信息。

## 4. 自动重连：存在于哪个项目

本仓库 Git 当前可见的 main 历史只有首次发布 `9fd92ad` 和 README 更新 `3cd3a4d`。

检查首次提交的 `src/client/session.ts`、`connection.ts`、`multi.ts`、`cli.ts`：已有 178 下发的跳转重连、持久客户端身份和 TCP 连接超时；没有在普通断线后自动退避重新启动会话的循环。README 的“重连带退避”是使用建议，不是内部实现。

CNKD 项目则确实有自动重连：

```text
CNKD NEXT 2.1.8(zhouhaoben)/headless-client/src/worker/room-worker.ts
```

- `reconnectDelay()`：5、10、20、40、60 秒，带约 ±10% 抖动，`:47-50`。
- `runLoop()`：每次从原始 roomCode 重新解析，再建 Session；可恢复失效的中继地址，`:137-168`。
- `disconnected` 触发重试；被踢、房间不存在等终态不反复重连，`:277-289`。
- 保留 clientUuid，再由各跳 serverUuid 派生身份。

这些结论来自当前本地文件核对，不代表今天已经检查生产进程、远端部署或 CNKD 早期 Git 提交。

## 5. 失联检测与重连是两个环节

| 当前层级 | 已有行为 | 缺口 |
|---|---|---|
| 主服务器 HTTP | 8 秒请求超时 | 本轮无需重复添加 |
| TCP/SOCKS 连接 | 7 秒协商超时，成功后 `socket.setTimeout(0)` | 连接后的沉默不会由这个定时器结束 |
| Session 握手 | 160/161/110/115 状态流 | 单房没有独立等待 161/注册结果的截止时间 |
| 入房后 | 定时发送 108、回答服务器 108；收到 socket close 发 disconnected | lastPongAt 只写不用于判断；没有基于接收活动的失联检测 |
| 多房 runner | 45 秒 settle 等待 | 超时仅记录 error，没有断开仍在连接的会话 |
| CNKD RoomWorker | 初次入房截止时间、断线后的退避重试 | 假在线不会触发 disconnected；joinedEver=true 后新一轮入房缺少有效的独立截止时间 |

原版 108/109 的方向尤其要注意：`02b/ad.java:2071-2123` 显示客户端收到服务器 108 时回 109，109 的 ping 统计主要由服务器处理。不能用“客户端没有收到 109”判定所有服务器都失联；应以收到的合理网络活动为主要依据。

本地 TCP 观察：沉默的已连接服务器让会话停在 awaiting-preregister；完成握手后保持沉默，客户端继续发心跳；服务器真正关闭 socket 后收到一次 disconnected，当前独立客户端没有再次拨号。每段观察窗口仅 200ms，用于核对事件流；“没有长期截止时间”的结论依据源码，而非把 200ms 当默认超时阈值。

## 6. 建议实现顺序

先修 115 的槽位、删除、观战、ping、共享控制语义，再补共享控制/暂停状态和对应变更事件。修复应使用按原版写侧构造的多槽位包，覆盖完整→精简→删除、观战变更、AI 混合、paused true/false 和缺省旧版本设置。

随后给 Session 增加可配置握手截止时间及接收活动失联检测：入房前总截止时间防止公告/重复挑战无限拖延，输入等待使用现有独立超时；入房后按接收活动和合理宽限判断，不能按聊天安静时间判断。单纯收到零碎字节也不应无限延长未完成一帧的等待。

失联时清理本跳定时器并只触发一次 disconnected，继续由 RoomWorker 负责退避重连；被踢、用户退出和房间不存在仍属终态。不在 Session、runner 和 Worker 三层各放一个自动重试循环。

CNKD Worker 还需给每次重连尝试独立的入房截止时间，避免第一次成功后新连接卡在握手阶段。独立 CLI 如果需要自动重连，可以新增明确的可选 runner，复用同类策略；这不属于目前已有的自动能力。

建议先完成名册修复再合并当前分支，状态和检测按同一套原始协议向量验证。密码输入按用户要求不列入本轮工作。
