# 房间号统一入房协议审计

日期：2026-10-09。对象：当前 `rw-headless` 与相邻 `rw_analysis` 的本地源码。

> 本文保留修复前的审计快照，文中的“当前实现”和 54 项测试结果指建分支前版本。随后已在 `codex/vanilla-room-join` 完成修复与真实入房测试，最终结果见 [VANILLA-ROOM-JOIN.md](VANILLA-ROOM-JOIN.md)。

## 结论

可以把原版支持的房间代码、连接描述符、IP/域名统一交给同一个入房状态机，不必按 R/S/Q 或 Rukkit/RW-HPS/CNKD 分别实现完整客户端。当前项目已经实现了房间代码的原版入口规则，主要欠缺在入口之后的协议一致性。

但“统一入房”不等于任意数字都能定位到任意服务器：代码必须是中继体系可解析的代码，或者用户提供可解析的连接描述符/地址。不存在、不公开且没有中继映射的房间，原版也没有通用发现能力。密码、版本、房间锁和网络可达性仍然影响入房。

本轮完成静态对照和本地构造包复现，没有修改运行代码，没有加入外部房间，也没有验证线上服务器的当前兼容性。

## 1. 原版如何解释用户输入

入口链路：`Root.joinServerFromPopup` → `joinServerWithId` → `joinServer` → `ad.b(String, boolean)`。

核心源码：

- `../rw_analysis/02b-decompiled/com/corrodinggames/librocket/scripts/Root.java:247`
- `../rw_analysis/02b-decompiled/com/corrodinggames/rts/gameFramework/j/ad.java:3553`
- 对照：`../rw_analysis/02-decompiled/com/corrodinggames/rts/gameFramework/j/ad.java:3215`
- 当前实现：`src/masterserver/target.ts:25`

原版按顺序执行：

1. `get|id|code|needsPassword|port`：调用主服务器 `action=get`，得到地址后递归调用同一个连接解析器。
2. 结尾 `.relay`：补 `.corrodinggames.com`。
3. 开头 `[TCP]`：去掉前缀，并强制 TCP。
4. 长度大于 4、不含 `:`、`.`、`/`、`\`、且不是 `localhost`：改写为 `<首字符>.relay.corrodinggames.com/<完整输入>`。
5. `/` 或 `\` 后的完整字符串作为查询串；前面的主机部分才解析连接端口，默认 5123。
6. 选择 TCP 或游戏自带的可靠 UDP，建立连接。

例如 `r12345` 会变成 `r.relay.corrodinggames.com/r12345`；`q12345` 使用同一条规则。这里没有按服务器品牌选择插件或解析器。例子仅用于展示规则，不代表这些房间存在。

四位纯数字不会命中代码规则；超过四位的纯数字会使用首位数字构造中继域名。能否入房仍取决于该域名和代码是否由实际基础设施提供。

当前 `parseConnectTarget` 已基本复现这个入口规则。固定的房间码前缀白名单不应成为客户端协议层的限制；如果上层机器人有这样的白名单，需要另行检查。

## 2. 原版中继跳转是结构化包

原版 `178 / PACKET_RECONNECT_TO` 的载荷：

```text
byte       一个读取后未使用的字段
int32      一个读取后未使用的字段
boolean    连接失败时是否执行重连失败提示/断开处理
int32      地址数量
UTF[]      按数量读取的 Java modified UTF-8 连接字符串
```

证据：`02b/.../j/ad.java:2938`、`02/.../j/ad.java:2209`。
布尔字段的实际用途见 `02b/.../j/ad$8.java:32`，不是强制 TCP 标志。

本源码快照的 `ad.a(ArrayList, boolean)` 只选择第一个地址，再调用通用连接器（`02b/.../j/ad.java:5957`）。所以不能把“自动尝试全部候选地址”描述成这里已经具备的原版能力；有序候选回退可以作为我们自己的增强。

当前 `src/client/session.ts:96` 与 `:198` 将整个二进制载荷转成 latin1，再正则扫描地址。这会绕过字符串边界和通用目标规则：

| 跳转里的合法连接字符串 | 原版/通用解析语义 | 当前扫描结果 |
|---|---|---|
| `example.com` | 默认连接 5123 | 找不到地址，忽略跳转 |
| `r12345` | 重新按代码规则解析 | 找不到地址，忽略跳转 |
| `[TCP]host.example:6000/room:7000` | 连接 6000，查询串是 `room:7000` | 连接 7000，查询串变成 `room` |

原版把路径内的冒号保留在查询串中。当前对 `host/room:port` 的处理是已有社区兼容解释，不能当作原版通用语法。

修正方向：先按字节结构读取 178，再把其中的完整字符串交给 `parseConnectTarget` / `resolveTarget`。确有抓包证据要求特殊解释的服务端偏差，集中在有限的兼容策略里，避免污染默认规则。

当前跳转次数达到 3 后仅记录日志并忽略。通用实现应明确报告循环/次数上限错误，并隔离旧连接事件，避免用户看到长期停留在连接中。

## 3. 哈希格式与原版不一致

原版 SHA-256 字符串使用大写、固定 64 位十六进制：`02b/.../gameFramework/f.java:557-597`。MD5 仍是小写，不应一并改成大写。

### 注册密码

原版注册密码是 `f.e(password)`，服务端用字符串精确比较：`02b/.../j/ad.java:2218`、`:4093`。

当前 `buildRegister` 使用小写 `sha256Hex`。同一个测试密码产生：

```text
当前：c638833f69bbfb3c267afa0a74434812436b8f08a81fd263c6be6871de4f1265
原版：C638833F69BBFB3C267AFA0A74434812436B8F08A81FD263C6BE6871DE4F1265
```

因此，对严格执行本源码密码比较的服务器，即使密码内容正确也无法通过。宽松社区实现是否接受小写，本轮未实测。

### 主服务器 p_hash

原版 `f.c(gameId + password, 3)` 共做四次 SHA-256，每一次的结果都转成大写字符串，再作为下一次输入。

证据：`02b/.../j/ab.java:29`、`02b/.../gameFramework/f.java:569`。

当前 `repeatHash` 每轮用小写。因此差别不仅在最终字母大小写，后续轮次哈希值也完全不同。本地固定输入的结果已复现不一致。

### 身份派生

原版 `Z()` 返回大写 `SHA256(baseClientUuid + serverUuid)`：`02b/.../j/ad.java:3998`。当前派生原则正确，但输出小写。

服务器可能把它当作不透明身份，所以不能仅凭大小写断言一定拒绝注册。不过若后续统一改为原版格式，已有部署在服务器侧可能被识别为新身份，需要考虑迁移影响。

应按协议用途定义明确的哈希函数，避免简单修改一个公共函数后同时改变不相关字段。

## 4. 151 挑战应保留状态并默认使用原版哈希

证据：`02b/.../j/ad.java:2626`、`02b/.../j/aq.java:23`。

原版两项挑战参数初始值为 55、66；只有下发包中的存在标志为真时才更新。因此，未携带某个参数意味着沿用旧值，而不是置零。

当前 `parsePowChallenge` 每次创建 null 参数，求解时替换成 0：

- 第一包 type 0、两个参数都缺省：原版应答 `55`，当前应答 `0`。
- type 6 不带第一参数：原版仍把此前参数追加到基串，当前没有追加。

当前 type 3/4/5/6 使用 `rwhpsPowHash14`，先删除 SHA-256 的前导零。原版 `f.c(String)` 是固定补零、大写、截前 14 位。

固定复现：输入 `audit-3` 的原版目标前缀为 `0B1ACB9CD5FB07`，合法解为 `3`，当前 solver 返回 `-1`。

建议默认按原版实现，并在确有社区偏差证据时提供集中的兼容选项。不能根据服务器名称就假定所有挑战采用同一种非原版格式。本轮没有重新核查 RW-HPS 服务端源码或线上行为。

## 5. 117 不是固定含义的“房间码请求”

原版读取 requestId 和提示文字，展示交互式输入；`113` 也会进入密码输入流程。

证据：`02b/.../j/ad.java:2512`、`:2378`。

当前 `onRelayPasswordRequest` 始终选择 `relayRoomId / pendingRelayRoomId / queryString`，没有通用输入回调，也没有在该链路使用 `opts.password`。这是房间码自动化特例，不能覆盖所有密码或其他输入请求。

通用客户端应提供包含 requestId、prompt、连接阶段的输入事件/回调。调用者可为已知入房阶段自动提供房间码，为密码阶段提供密码；不能仅靠某一种中文提示推断所有服务器的语义。无法确定时应等待输入或明确结束。

## 6. 主服务器竞争请求与版本边界

### 竞争请求

原版优先选择协议头有效且不带 `[FAILED]` 的响应：`02b/.../j/n.java:108-181`、`:241`。

当前 `fetchFirstValid` 仅检查 HTTP 状态后就让 `Promise.any` 选中响应；协议头校验在选中之后才执行。一个更快的 HTTP 200 错页或失败响应可能挡住另一个节点的有效结果。

应把协议有效性校验放到每个竞争请求内部，并在结束时清理其他请求。

### 版本和传输

当前只实现 TCP。原版支持配置选择可靠 UDP，`[TCP]` 用于强制 TCP（`02b/.../j/ad.java:3626-3741`）。要求覆盖 UDP-only 目标时，需要增加通用可靠 UDP 传输层，不是增加某品牌服务器适配器。

原版注册发送自身协议版本、构建版本和核心单位校验和（`02b/.../j/ad.java:4080`），不是简单用服务器回显值替换自身版本。当前回显 networkVersion 同时固定报告 176、默认使用 176 checksum，不能据此声称任意版本都兼容。

严格服务端会检查版本、核心单位和完整性（`02b/.../j/ad.java:2188-2209`）。若需要多版本入房，应按版本建立一致的协议配置和校验常数。无需为了战役室聊天移植整个游戏引擎，但当前聊天客户端也不因此获得完整对局同步能力。

## 7. rw_analysis 的源码使用边界

`03-deobfuscated` 便于定位，但本轮发现其关键逻辑有重建错误：

| 位置 | 03 的内容 | 两份原始反编译内容 |
|---|---|---|
| `NetEngine.java:3254` | `get|` 代码字段读 `[0]`，即 `get` | 读 `[2]` |
| `NetEngine.java:2584` | 第二个 type 0 条件执行 g() | 应为 type 2 |
| `NetEngine.java:4238` | `7:` 使用加法 | 使用乘法 |

这说明“能编译/整体回放验收通过”不能代替各网络分支的协议验收。后续应以 02 与 02b 的一致证据、原始字节码或真实抓包建立协议向量，避免直接复制 03 中的错误逻辑。

本轮对 178、房间代码规则、挑战 type 2 做了 02/02b 交叉核对；其他字段以 02b 中具体调用链为依据。未执行原始游戏 JAR。

## 8. 建议改造顺序与验收

1. 先统一 178 的结构解析和目标解析器，保留完整查询串，明确连接失败/循环的终态。
2. 修正注册密码、p_hash、挑战哈希和挑战参数状态；为身份格式变更安排迁移。
3. 增加 117/113 的输入事件，统一房间码、密码和其他提示的处理。
4. 修正主服务器有效响应选择，建立版本配置；可靠 UDP 按覆盖需求追加。
5. 用原版协议向量和本地假服务器覆盖上述分支，再用受控真实房间验证“进入正确房间”和聊天回显。

推荐结构：

```text
用户输入
  → 统一目标解析器（代码 / get| / 地址 / 查询串 / 传输）
  → 通用连接器（TCP，后续可加可靠 UDP）
  → 同一个会话状态机
      160/161/110 注册
      151/152 有状态挑战
      117/118 与 113 输入流程
      178 结构解析 → 返回统一目标解析器
      115/106 → 房间状态、玩家名册、聊天
```

不要以收到公告、TCP 已连接、已发注册包作为进入目标房间的证据。验收需要名册/房间信息及受控房间身份核对；聊天发送还需要接收端回显证据。

### 本轮验证结果

- 现有测试：8 个文件、54 项通过。
- 类型检查：`npm run typecheck` 通过。
- 另行本地构造包复现：注册密码大小写、迭代 p_hash、前导零挑战、缺省挑战参数、无端口域名/代码跳转、路径冒号端口解释差异。
- 测试首次在沙箱内因 Windows realpath EPERM 无法加载源码；以正常权限重跑后通过，未修改测试或依赖。
- 现有测试不包含主服务器响应竞争、完整二进制 178 或原版 PoW 固定向量；部分哈希测试直接断言当前小写输出，因此通过不代表与原版一致。
- 外部房间入房与当前服务器品牌兼容性：本轮未验证。

结论适用范围是：技术上能够围绕原版协议实现统一入房，目前实现仍有明确缺口；与原版不兼容的社区扩展仍可能需要小范围兼容处理，无法通过“统一解析”消除服务端自身的协议差异。
